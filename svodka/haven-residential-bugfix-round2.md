# Empery Haven — второй раунд правок жилого района (баги пользователя)

Жалоба: могилы на улице, NPC застряли/летают сквозь дома, пшеница на территории,
баскетбольная площадка наехала на сушку/дом, дети стоят рядами, указатель
перекрыт домом — «и это только жилой район, в остальных то же самое».

## Что было реально не так

### 1. Guard/ambient пути всё ещё резали дома (citizenPathIssues 7→0)
`haven-aabb-audit.mts` проверяет не только точки маршрута, но и **отрезки**
между ними (Liang-Barsky). Дотянул до 0 пересечений:
- `NIGHT_GUARD_PATROLS[4]` (жилой квартал) — диагональ `(28,44)→(26,42)` резала
  виллу/особняк, стоящие впритык (0 зазора в террасном ряду). Обошёл через
  восточный край ряда: `[31,44]→[34,43]→[34,40]`.
- `merchant` — вертикальный обход у `tx44` резал часовую башню/фонарь; сдвинул
  весь маршрут на `tx46`.
- `radio` — короткий отрезок у `tx39` резал скамейку; сдвинул на `tx41`.
- Восточный ночной патруль (`NIGHT_GUARD_BARKS[6]`) теперь заходит прямо на
  пост у `prop_watch_house` (`[74,28]`) без обходного «туда-обратно» огрызка.

### 2. Молчаливое исчезновение декора — вторая, нелогируемая точка дропа
`resolveHavenPropOverlaps` в `scripts/layouts/empery_haven.mjs` дропал предметы
**двумя** путями:
- явный (`if (!found) console.error('[drop]', ...)`) — виден через
  `HAVEN_DEBUG_DROPS=1`;
- **скрытый**: после `ringSearch` шёл отдельный "hitKept" AABB-чек против уже
  расставленных пропов, который просто делал `continue` **без единого лога**.
  Из-за этого фонтан, беседка, детская площадка, классики и арка квартала
  тихо пропадали с карты — не «наехали», а именно исчезали, и в отчёте дропов
  их не было видно вообще.

Фикс: `spriteHitsKept(x,y)` теперь часть условия запуска `ringSearch`, и сама
проверка используется **внутри** ring-перебора кандидатов — предмет ищет
свободное место с учётом обеих проверок (занятость тайлов **и** визуальный
AABB против уже уложенных), а не падает после первой неудачной попытки.
Восстановлено decor: `prop_yard_fountain`, `prop_garden_pergola` (дворик),
+12 пропов итого (455→467). `prop_playground_sandbox` / `prop_hopscotch` /
`prop_neighborhood_gate` всё ещё не помещаются даже в радиусе 10 — дворик
объективно перегружен (см. TODO ниже), но теперь это видимый `[drop]`, а не
немая пропажа.

### 3. `prop_neighborhood_well` считался «уникальным зданием» → улетал на 13 тайлов
`isUniqueBuildingId()` — эксклюзия-регэксп для мелкого декора неполный: в нём
не было `neighborhood_well`, поэтому колодец получал `searchR=20` (радиус для
маяков/ратуш), и при тесноте укатывался аж к некрополю (tx8.5,ty54.5) —
и правда «наехавший на кладбище колодец». Добавил в список исключений →
теперь смещается на 2–3 тайла, а не через весь квартал.

### 4. Дети «стоят рядами по 4» — реальный баг офсета сна
`resolveAmbientSleepTile()` в `packages/shared/src/haven-npc-homes.ts`:
```js
const ox = ((index * 3) % 3) - 1; // ЛЮБОЕ index*3 делится на 3 без остатка!
```
`ox` был **константой `-1` для абсолютно любого NPC** — вариативность давал
только `oy` (3 значения). Итог: все жители, которым выпадал один и тот же
"домашний" тайл кластера (`AMBIENT_HOME_PARK`/`TENEMENT`/...), ночью съезжали
в один и тот же X со сдвигом только по Y на ±1 — визуально «стоят в ряд/друг
на друге» у дома. Заменил на честный 3×3 скаттер:
```js
const slot = Math.floor(index / cluster.length) % 9;
const ox = (slot % 3) - 1;
const oy = (Math.floor(slot / 3) % 3) - 1;
```

### 5. Указатель «Спальный» перекрывался домом
Уже был сдвинут в прошлом раунде на `c(16,46)`. Заодно поправил соседний
"Общинный сад" — его дробная координата `c(27,44.6)` из прошлого раунда ловила
не дом, а тест `haven-object-census.test.ts` (YAML-парсер сравнения регэкспом
`\d+` не понимает дробные `y`). Заменил на целую `c(27,45)` — попадает в тот же
зазор между рядами домов, тест снова зелёный.

### 6. «Баскетбольная площадка наехала на сушку/дом»
В коде нет prop с именем `basketball` — по описанию это `prop_playground_sandbox`
/ `prop_hopscotch` (детская площадка/классики) в том же перегруженном дворике,
что и в п.2: раньше пакер тихо телепортировал/накладывал их через hitKept-баг
без лога. После фикса они либо ложатся чисто, либо просто **не размещаются**
(видимый `[drop]`) — уже не наезжают на сушку/дом, но дворик реально нуждается
в разгрузке (TODO).

## Раунд 3 — реальная причина «дети стоят в доме»

Предыдущий фикс (п.4 выше, честный 3×3 скаттер офсета) был **недостаточным** —
он лечил повторяющиеся координаты, но не проверял, не попадает ли итоговый
тайл ВНУТРЬ здания. Проверка в упор:

```ts
// AMBIENT_HOME_* — 4-6 захардкоженных тайлов на весь квартал, никогда не
// сверялись с реальной (много раз перестраивавшейся) раскладкой домов.
for (const d of ALL_CITIZEN_DEFS) {
  const [tx, ty] = resolveAmbientSleepTile(...);
  // сравнил с солид-боксами домов/tenement_block
}
```
Результат: **37 из 147** амбиент-жителей получали ночную точку сна ПРЯМО
внутри дома/колосса (после offset, даже базовый тайл кластера рядом с домом
после сдвига ±1 тайл заезжал на стену). Ночью житель идёт туда пешком
(`walking_home` → `beginStreetRoute`), не может дойти до недостижимой точки
внутри стены и застревает вплотную к зданию — визуально «стоит в доме».
Это била не только детей — human/orc/mira/captain и т.д. по всей карте.

Фикс: экспортировал `snapAmbientHomeTile()` из `haven-ambient-defs.ts`
(тот же collision-snap, что уже используется для явных `sleepTile`) и применил
его к каждому ВЫЧИСЛЯЕМОМУ (не явному) sleep-тайлу в `resolveSleepTile()`
(`haven-citizens.ts`). Теперь ни один житель не получит точку сна внутри
здания — если кластер-тайл занят домом, житель отодвигается на ближайший
свободный тайл тем же алгоритмом, что и патрули/явные точки.

Это правки в клиентских `.ts`-файлах (не через `@empery/shared` dist) —
подтягиваются Vite HMR сразу; если всё равно не видно — жёсткий
Ctrl+Shift+R / перезапуск `pnpm dev:client` (в проекте есть service worker
`apps/client/public/sw.js`, который может отдавать старый бандл из кэша).

## Раунд 4 — `start-all.sh` реально мог отдавать старьё

Не в правках карты, а в самом скрипте запуска было три дыры, из-за которых
пересборка НЕ гарантировала свежий контент в браузере:

1. Админка не билдилась вообще (`tsconfig.json` не листил
   `prop-footprint.ts`/`prop-layer.ts`, транзитивно нужные `haven-ambient-defs.ts`
   через новый `apps/admin/src/haven-map.ts`) → `set -euo pipefail` валил
   **весь** скрипт на шаге admin-build, и блок запуска серверов (после build)
   просто никогда не выполнялся. Добавил оба файла в `include`.
2. Никакой очистки портов перед стартом: если с прошлого запуска (или
   `pnpm dev:server`/`dev:client`) на 3000/5180/5190 висел старый процесс —
   новый `tsx`/`vite preview` либо не мог забиндиться и тихо умирал в фоне,
   либо (что хуже) просто МОЛЧА не запускался, а браузер продолжал стучаться
   в старый живой процесс — пересборка происходила, но результат никто не
   видел. Добавил `empery_free_port(s)` в `lib/env.sh` (kill по `fuser`) и
   вызов `empery_free_ports 3000 5180 5190` в начале `start-all.sh`.
3. Скрипт не гонял `pnpm generate:maps` — если кто-то правил
   `scripts/layouts/empery_haven.mjs` и забыл руками регенерировать
   `haven-city-data.ts`/`haven-ambient-defs.ts`/карты, `start-all.sh` собрал
   бы билд из СТАРЫХ сгенерированных файлов. Добавил `pnpm generate:maps`
   перед сборкой — теперь скрипт сам приводит сгенерированные файлы в
   соответствие с layout-скриптами при каждом запуске.
4. `vite preview` запускался без `--strictPort`, и после старта скрипт не
   проверял, что новые PID реально живы/слушают — просто печатал "готово".
   Добавил `--strictPort` + explicit liveness-check (`kill -0`) + `curl`
   health-check на 5180/5190 перед финальным "✓ всё живо".

Проверено полным прогоном `bash scripts/start-all.sh` — все три порта
(3000/5180/5190) отвечают 200, `/health` зелёный, сервер реально проксирует
WS/API-запросы.

## Раунд 5 — вот он, реальный «баскетбол наехал на дом»

Скриншот пользователя (`download (2).png`) наконец дал прямое визуальное
подтверждение. Причина оказалась не в пакере (`empery_haven.mjs`) и не в
амбиент-путях (`haven-ambient-defs.ts`) — а в третьем, полностью отдельном
файле: **`apps/client/src/sprites/haven-residential.ts`**. Он рисует «жизнь
дворика» (баскетбол, дети, кот, пёс, ночной дозорный, курьер, колодец,
торговец у лавки, фонтан-искры и т.д.) по ЖЁСТКО прописанным координатам
тайлов — независимо от пакера и его коллизий. Эти координаты один раз
подобрали под ТУ раскладку домов, что была на момент написания файла, и с тех
пор ни разу не пересчитывали, хотя `buildHavenResidentialLayout` переписывался
многократно за эту сессию.

Прогнал все точки этого файла через проверку "лежит ли внутри бокса
дома/tenement_block текущей раскладки":

```
well (13,45) -> INSIDE tenement
hopscotch (17,45) -> INSIDE tenement
cat1a (12,44) -> INSIDE prop_house_row
cat1c (19,45) -> INSIDE tenement
... (итого 27 точек из ~40)
```

**27 из ~40 хардкод-точек лежали прямо внутри дома или тенемента** — отсюда
и баскетбольная площадка, «наехавшая» на `prop_house_townhouse`, и дети/кот/
пёс/дозорный/курьер, гуляющие сквозь стены домов (визуально — «стоят в
доме»). Именно это видно на скриншоте: площадка впритык к дому, подпись
«Дом жильцов» перекрыта соседним домом, лавочник стоит не у своей лавки
(`prop_house_corner_shop` давно переехал с (10,45) на (25,47), а торговец
всё ещё «продавал» у старого адреса).

Написал скрипт (`nearestClear`), который ищет ближайший тайл вне всех
домов/tenement для каждой плохой точки, и вручную перепроверил площадку
отдельно (у неё большой footprint — 220px, простой point-check не годится;
перебрал кандидатов по минимальной площади пересечения). Итог правок в
`haven-residential.ts`:
- баскетбольная площадка: (21,45) [впритык к townhouse] → (21,40)
  [минимальное пересечение — только угол workshop_home; в этом дворике
  физически нет тайла с нулевым пересечением при таком размере площадки];
- колодец-болтовня: (13,45) [пустое место] → (17,38) [совпадает с реальным
  `prop_neighborhood_well`];
- классики: (17,45) [внутри tenement] → (16,46);
- оба кота-бродяги (10 точек), пёс (3 точки), курьер (4 точки), ночной
  дозорный (5 точек), light-glow, обедающие соседи, голуби, одна точка
  сушки белья — у каждой подобрана ближайшая свободная точка;
- искры фонтана: (13,48) [пусто] → (19,46) [совпадает с реальным
  `prop_yard_fountain`];
- торговец лавки: (10,45) → (25,47) [реальная позиция `prop_house_corner_shop`].

Оставил как «намеренно внутри» только 2 случая: (а) колодезная болтовня в
упор к самому колодцу — так и задумано; (б) якорь торговца лавки совпадает
с самим домом лавки ДО применения смещения «+8,+70 к югу от фасада» — тоже
корректно.

Проверено: `tsc --noEmit` чист, **39/39 client test-файлов (155/155 тестов)**
зелёные, `pnpm --filter @empery/client build` собирается (хэш чанка
`create-game-*.js` реально изменился — подтверждает, что билд не кэшировал
старьё, прошлые опасения по этому поводу были ложной тревогой).
